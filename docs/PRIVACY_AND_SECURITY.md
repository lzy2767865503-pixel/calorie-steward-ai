# 卡路里管家隐私与安全基线

## 实际数据流

1. 用户只能通过 App 相机拍摄餐食；客户端不请求相册全库权限。
2. 图片在本机缩放到最长边 1600 px、重新编码为 JPEG，并不复制 EXIF/GPS。
3. 用户明确同意后，重编码图片发送到其选择的 AI Provider 或自有 HTTPS 代理。调用费用和 Provider 侧保留政策由该用户账户承担。
4. Provider 返回必须符合严格结构；不合法、拒绝、非食物、需要重拍或无法量化时，App 不写入餐食记录。
5. 用户确认后，结构化餐食写入本机 SQLite。原始照片默认删除；只有在设置中开启“今后保留”时才复制到 App 私有目录。
6. 生成饮食报告时，AI 只接收本机已计算的匿名时间汇总、指标区间、覆盖率与确定性分类；不接收照片、姓名、精确位置或 API Key。

## 已实现的控制

- 已发布 Android 清单与 iOS 源码配置都只声明相机能力，不声明录音权限；iOS 本次未构建或运行验收。
- 远程端点必须是 HTTPS。只有开发构建可以连接 `localhost` / `127.0.0.1`。
- 图片 MIME 与文件魔数必须一致，请求和响应均有大小、超时与结构限制。
- API Key 由 SecureStore 持有，并按 Provider 类型、端点 origin 与认证类型绑定；SQLite 只保存 Provider 类型、端点、模型和密钥末四位状态。切换厂商、origin 或认证类型后必须重新输入密钥并重新同意照片发送目标，旧密钥绝不跨域复用。
- 业务记录使用 SQLite 事务、外键、WAL 和版本迁移；修改或删除餐食会强制当日回到“未完整”并重算所有周期。
- 导出 JSON 结构性排除密钥、照片和本机文件路径。
- “删除全部饮食数据”会在事务中删除餐食、日状态与报告，并尝试清理已保留的本地照片。
- 无 Demo 降级、无固定营养值、无旧图结果复用。

## BYO-key 的边界

SecureStore 可降低普通本场泄露风险，但无法把安装在终端上的长期 Provider 密钥变成绝对安全。

- 个人测试：可使用自己的限额 Key，开启 Provider 费用上限和异常警报，不应使用管理员级密钥。
- 企业发布：建议连接用户/企业自有 HTTPS 代理，在服务端密钥库中保存 Provider 密钥，并实施用户鉴权、限额、幂等、审计和撤销。

## 生产上线前必须完成

1. 对每个可选 Provider 记录数据处理地区、保留期、训练政策、子处理方和删除 SLA。
2. 完成 DPIA/隐私影响评估、威胁建模、依赖扫描和恶意图片解码隔离。
3. 将“当次识别”与“用于模型训练”设为分开、可撤回的同意；当前 App 不提供训练上传。
4. 完成 Google Play Data Safety 与 Apple App Privacy 申报，使其与最终网络、分享、保留和删除行为一致。
5. 使用企业签名、锁定依赖且可审查/可重复执行的 CI 构建流程、SBOM、应用完整性与发布审批；如要宣称比特级可复现，还需另行建立并验证确定性构建。

## 非目标

- 不在未取得明确同意时保存或上传用户照片用于训练。
- 不使用 AI 文本代替本地确定性分数。
- 不作诊断、治疗、药物调整或医疗设备声明。
